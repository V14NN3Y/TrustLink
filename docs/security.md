# Security model

## Principles

1. **The client is untrusted.** The anon key is public and every user controls their own requests. Anything that matters (roles, amounts, payment, status transitions) is decided in the database or an Edge Function.
2. **RLS on every table.** A table without a policy for an action denies that action.
3. **Narrow server functions instead of broad policies.** Buyers have no `update` on `orders`; each legitimate transition has its own `SECURITY DEFINER` function that re-checks ownership and the current status.
4. **The service-role key never leaves the team's machines / Supabase secrets.** It bypasses RLS. Never put it in a `VITE_` variable.

## Roles and admin accounts

- Sign-up always creates a `buyer`. The `role` sent in sign-up metadata is ignored.
- An account becomes `admin` only if its sign-up carries a valid, unused `invite_code` from `invitation_codes`; the code is consumed in the same transaction.
- Codes are generated by an admin (Profile → Team → Invite a member) and expire after 30 days.
- `role`, KYC flags and `business_slug` can only be changed by an admin, the SQL editor or the service role (`trg_profiles_protect_privileged`).

## What each role can do (summary)

| Data | Buyer | Admin |
|---|---|---|
| Own profile | read, update (not role / KYC) | all profiles |
| Products, categories | read published | full |
| Cart, wishlist | own | — |
| Orders | read own, create via RPC, delete own `pending` | full |
| Tracking events, inspections | read own (visible inspections only) | full |
| Disputes, delivery videos | own (create via RPC) | full |
| Notifications | read / mark read own | create, read all |
| Messages | sent or received | sent or received |
| Stock alerts | subscribe | full |

## Storage

| Bucket | Read | Write |
|---|---|---|
| `product-images`, `avatars` | public | admin (products), owner (avatar) |
| `delivery-videos` | owner, admin | only `confirmations/<uid>/` and `disputes/<uid>/` of the caller |
| `inspection-photos` | admin; buyer for visible photos of own orders | admin |
| `kyc-documents` | owner, admin | authenticated, admin |

## Payments

The KkiaPay widget runs in the browser, so its "success" event proves nothing. `verify-payment` asks KkiaPay directly, checks the amount against the server-computed total and refuses a transaction already used for another order.

## Checklist for new code

- New table → `enable row level security` + explicit policies for each action needed.
- New bucket → policies scoped by path (`split_part(name, '/', n)`).
- Status change by a buyer → a dedicated RPC, never an `update` policy.
- Amounts → computed in SQL, never trusted from the client.
- Add the attack to `supabase/tests/security_attacks.sql`.
